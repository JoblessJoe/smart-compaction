Message threads

Give long-running agents a faster time to first token, especially in long conversations, by sending only the new messages on each request.

With a message thread, requests are smaller, and time to first token stays lower and steadier as the conversation grows. Threads help most in long agent loops. Without a thread, every turn uploads the whole conversation again, and the API validates and tokenizes all of it again. With a thread, most of that work covers only the new turn.

A message thread keeps a conversation on the server for a short time. You send the full conversation, your system prompt, and your tools once. On each later turn, you send the new messages and the id of the previous response instead of the full conversation. The API rebuilds the conversation before it calls the model. You add the threadPreview with links to the API reference available — press Tab until focus enters the card, Escape to return. parameter and a beta header to a Messages API request. The response is the usual message.



Message threads are different from session threads in Claude Managed Agents.

How message threads work

  • Create. Send your first request as you do today, with the full conversation, system, and tools. Add "thread": {"type": "create"} to the request. The API stores the conversation, including Claude’s reply, under the response id.
  • Continue. Send only the messages since the previous response and add "thread": {"type": "continue", "previous_message_id": "<previous id>"}. Leave system and tools out of the request. The thread keeps the values from the create request. Use each new response id for the next turn.
  • Replay. A thread is best-effort. It expires 5 minutes after its last request, and the API deletes it no more than 1 hour after its last use. Each response that the API stores restarts the 5 minutes. If the API can no longer continue the thread, a continue request returns a 404 error. Send the full conversation again in a new create request and continue from the new response id. The SDK thread helper does this replay for you (see How the SDK helper behaves). After a response from a fallback model, see Use fallbacks with a thread.

Your application stays the source of truth for the conversation. Keep your own copy of every message and build the replay path from the start. No response to a create or a continue request says whether the API stored that turn. You find out on the next continue request. The SDK thread helper keeps this copy in memory while the helper object exists, and it saves the copy nowhere else. If the conversation has to outlive your process, keep your own copy.

Use a thread with the SDK

The SDK has a thread helper that builds each request for you. Create the helper with the same fields as a Messages request. Then send one turn at a time. The helper keeps the full conversation in memory.

This example has two turns. The helper creates a thread on the first turn and continues it on the second, and it adds the beta header for you. The top-level cache_control is optional. It asks for prompt caching on each turn (see Prompt caching on a thread). Without it, each later turn still sends only the new messages, but nothing is cached unless you add cache breakpoints yourself.

Python
client = anthropic.Anthropic()

# Create the helper. This call sends no request.
thread = client.beta.messages.thread(
    model="claude-opus-5-5",
    max_tokens=1024,
    cache_control={"type": "ephemeral"},
    system="You are a support agent for Acme. Keep replies short.",
)

# Turn 1: the helper creates a thread and sends the full conversation
thread.send({"role": "user", "content": "Hi! I have a question about an order."})

# Turn 2: the helper continues the thread and sends only the new message
second = thread.send(
    {"role": "user", "content": "How long does standard shipping usually take?"}
)

for block in second.content:
    if block.type == "text":
        print(block.text)

Send the thread field yourself

Add the thread field to each request yourself. You can do this with cURL, with the CLI, or with an ordinary SDK request.

Send the message-threads-2026-08-12 beta header on every request of a thread.

This example creates a thread on the first turn and continues it on the second. The top-level cache_control asks for prompt caching on each turn. Nothing is cached until the full conversation, together with system and tools, reaches the minimum cacheable length.

Python
client = anthropic.Anthropic()

# Turn 1: send the full conversation and create a thread
first = client.beta.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    cache_control={"type": "ephemeral"},
    system="You are a support agent for Acme. Keep replies short.",
    messages=[{"role": "user", "content": "Hi! I have a question about an order."}],
    thread={"type": "create"},
    betas=["message-threads-2026-08-12"],
)

# Turn 2: send only the new message and the id of the turn 1 response.
# Leave out system and tools: the thread keeps them.
second = client.beta.messages.create(
    model="claude-opus-5-5",
    max_tokens=1024,
    cache_control={"type": "ephemeral"},
    messages=[
        {"role": "user", "content": "How long does standard shipping usually take?"}
    ],
    thread={"type": "continue", "previous_message_id": first.id},
    betas=["message-threads-2026-08-12"],
)

for block in second.content:
    if block.type == "text":
        print(block.text)

What to send on each request

GroupFieldsRule
Create-onlysystem, toolsSend them on the create request only, with any cache_control breakpoints on them. Sending either one on a continue request, even as null, returns a 400 error.
Fixedmodel, tool_choice, thinking, mcp_servers (apart from each server’s authorization token), context_management, output_config, the skills in container, the top-level cache_control, and the set of anthropic-beta valuesSend them on every request of the thread, with the same values as on the create request. A different value returns a 400 error with the code thread_fingerprint_mismatch, and the error message names the fields that differ.
Freemax_tokens, stop_sequences, stream, metadata, service_tier, and other fields not named on this pageThese can change from turn to turn.

The API does not store MCP server URLs, MCP authorization tokens, or the container id. Send mcp_servers and container on every request that uses them. An MCP authorization token can change between requests.

The SDK thread helper leaves system and tools out of continue requests for you and sends the fixed fields again on every turn.

If you use server-side fallback, send the fallbacks field on every request of a thread or on none. See Use fallbacks with a thread.

To change a create-only or fixed field, start a new thread: send the full conversation in a create request with the new values.

If you change system or tools: On the following models, leave every thinking and redacted_thinking block out of the conversation that you send in the new create request: Claude Fable 5.2, Claude Mythos 5.2, Claude Fable 5.1, Claude Mythos 5.1, Claude Opus 5.5, Claude Sonnet 5.5, and Claude Haiku 5.5. The model then answers without that earlier reasoning.

  • Why: Changing system or tools makes the thinking and redacted_thinking blocks already in the conversation invalid. See What counts as a change.
  • If you send the blocks anyway: The create request can get a 400 error (see Thinking block bound to a different conversation). See Which models run the prefix check.

Send only the new messages on a continue request. The API doesn’t check them against the messages it already has. A message you send again can appear twice in the conversation, or the request can return an error. For example, a continue request that starts with the previous response returns an error.

The new messages usually start with a user message: your next user turn or the tool_result blocks that answer a tool_use in the previous response. If a response stops with stop_reason: "pause_turn", resume it with a continue request from that response’s id and an empty messages list ("messages": []). If that request returns a 404 error, replay the full conversation, including the paused response, in a new create request. Don’t send a new user message while the turn is paused: the API rejects it. With the SDK thread helper, call send() with no messages: the helper sends this request and replays on a 404 error.

A thread is append-only, and each response id can be continued once. Always continue from the latest response id of the thread. To edit or branch an earlier message, start a new thread with a create request. To replace earlier turns with a summary, see Compact a conversation.

Prompt caching on a thread

A thread does not cache your prompt for you. Prompt caching works as it does without a thread: you choose where the cache breakpoints go.

To cache each turn, send a top-level cache_control on every request of the thread as in the earlier example. The API applies it to the last block of each request’s messages that can be cached. Each turn then reads the earlier conversation from the cache and writes the new turn to it. The top-level cache_control is a fixed field: send the same value on every request.

You can also place cache_control breakpoints on blocks yourself:

  • Breakpoints that you send on the create request keep working on every later turn if they are on tools, on system, or on a message block before the last one. A breakpoint on the last block of a request’s messages writes the cache on that request. To cache each new turn, send a breakpoint on every request. A request without a breakpoint might still read part of the conversation from the cache.
  • You can’t move or remove a breakpoint after you send it, because a continue request can’t send an earlier message again.
  • A request with thread can carry at most 4 cache_control breakpoints. The top-level cache_control counts as one. Breakpoints on the system and tools of the create request count again on every continue request. Breakpoints on earlier stored messages do not count. One breakpoint too many returns a 400 error with the code thread_unsupported_request.
  • If you place breakpoints on message blocks yourself, remove them from earlier messages and keep one on the last block when you replay the conversation in a new create request. The request then stays within the limit of 4.

Streaming

Threads work with streaming. The response id arrives in the message_start event, but continue from it only after you receive the message_stop event. A continue request sent earlier can return a 404 error.

If the stream of a continue request drops before message_stop, send the same continue request again. If that request returns a thread_already_continued or thread_continue_in_flight error, replay the full conversation in a new create request.

Your connection might have dropped while the server was still generating the response or after the server saved it. That is why the API can reject the retry. Replaying your exact copy is safe.

The SDK thread helper doesn’t retry the continue request after a dropped stream. See How the SDK helper behaves.

Recover when a thread can’t be continued

A continue request returns a 404 error with error.details.error_code set to thread_not_found when the API can’t continue the thread. The response does not say why. The causes include the following:

  • The thread expired.
  • The API served the previous turn but did not store it. For example, the API does not store a response that ends in a tool call cut off by max_tokens.
  • A fallback model wrote the previous response. See Use fallbacks with a thread.
  • The previous response is still generating.
  • The request comes from a different organization or workspace.
  • The request comes from a different user or service account from the one that created the thread. A thread created with a workspace key (legacy) stays with that key, so use the same key for the whole thread.
  • The new messages add something that the stored conversation can’t take. For example, the first image in a conversation that had none can return this error.

To recover, follow these steps:

  1. If earlier messages in your own copy of the conversation carry cache_control breakpoints, remove them (see Prompt caching on a thread).
  2. Send the full conversation from your copy in a new create request with system and tools.
  3. Continue from the new response id.

The SDK thread helper sends this create request once by itself. When it does, it leaves out the cache_control breakpoints of earlier turns.

If a fallback model wrote the previous response, see Use fallbacks with a thread.

Some of these causes depend on who sends the request. To rule them out, use the same workspace and the same API key, user, or service account for every request of a thread. On Claude Platform on AWS, sign every request of a thread with credentials for the IAM role or IAM user that created the thread.

A request for a model that does not exist also returns a 404 error, so check error.details.error_code before you replay.

If a continue request still returns a 404 error right after you replay, the API might be unable to store that conversation (for example, a very large one). Send it without thread. The SDK thread helper does this when you create it with unsupported_request_behavior set to continue_unthreaded. Otherwise, the helper replays on every turn.

After a refusal

When a response has stop_reason: "refusal", do not continue the thread. The API might already hold the refused turn, and a continue request can’t remove it. Start a new thread with a create request that leaves out or rephrases the turn that led to the refusal. See Refusals and fallback. The SDK thread helper does this for you: it doesn’t keep the refused turn, and its next turn starts a new thread.

Use fallbacks with a thread

Server-side fallback is available with threads on the Claude API. Decide when you create the thread: send fallbacks on every request of the thread or on none. The value of fallbacks can change between requests. A continue request that adds or drops fallbacks returns a 400 error with the code thread_fingerprint_mismatch.

A thread keeps one model, so the API doesn’t store a turn that a fallback model wrote. You get the response as usual, but you can’t continue from its id. After each response, follow these steps:

  1. If stop_reason is "refusal", follow After a refusal.
  2. Otherwise, look for a fallback_message entry in usage.iterations. On a stream, read it from the final message_delta event. If there is none, continue the thread as usual.
  3. If there is one, a fallback model wrote the response. Send the full conversation, including that response and your next message, in a new create request. Keep the server-side-fallback-2026-07-01 beta header on it. Choose one of these two requests:
    • The same request again. Keep model, fallbacks, and your other parameters as they were. If the model you requested answers, the API stores the new thread. If a fallback model answers, the response has a fallback_message entry again and the API doesn’t store it, so repeat this step on the next turn. Sticky routing might send these requests straight to the fallback model, so every turn might send the full conversation. The SDK thread helper works this way.
    • A new thread on the fallback model. Set model to the model in that fallback_message entry, leave fallbacks out, and use parameters that this model accepts. The API stores this thread at once, and it stays on the fallback model. The fallback attempt might have run with different settings from the ones you sent, so the API might reject values copied from your first request.
  4. Go back to step 1 with the response to that request. When it has no fallback_message entry, continue the new thread from its id.

Sticky routing starts after a request falls back (a create request or a request without thread). For about an hour, it might send later create requests for the same conversation that include fallbacks straight to the fallback model without trying the model you requested. The API stores none of those turns, and each answered one restarts the hour. A continue request never starts this routing and never uses it. Sticky routing doesn’t apply if your organization or workspace uses zero data retention or customer-managed encryption keys.

Compact a conversation

A thread is append-only, so you can’t replace its earlier turns with a summary. To compact a conversation, start a new thread from the summary. Write the summary in your code and send it as an ordinary message in a new create request with system and tools. Compaction on demand is not available with threads (see Features that threads don’t support).

How the SDK helper behaves

What the helper does for you:

  • Adds the message-threads-2026-08-12 beta header to every request that uses the thread.
  • Creates a thread on the first turn and continues it after that, sending only the new messages and leaving out system and tools.
  • Replays the full conversation once in a new create request when a continue request returns thread_not_found, thread_already_continued, or thread_continue_in_flight.
  • Resumes a pause_turn response when you call send() with no messages.
  • Starts a new thread after a refusal. You get the stop_reason: "refusal" response as usual, but the helper doesn’t keep that turn: it takes back the messages you gave to that call. Messages that you added with thread.append(...) or gave when you created the helper stay staged. Your next turn sends them in a new create request with the conversation from before the refused turn. Send a rephrased message or, if a staged message led to the refusal, start a new thread from the params without that message.
  • Sends a new create request after a response from a fallback model. When a response has a fallback_message entry in usage.iterations, the helper keeps the response and sends the full conversation in a new create request on the next turn. It doesn’t wait for a 404 error. That request keeps the model and fallbacks that you set.
  • Leaves out the cache_control breakpoints of earlier turns whenever it sends those turns again (for example, in a replay or in the first turn of a fork). Your newest messages, system, tools, and the top-level cache_control go out as you gave them.

What you handle yourself:

  • Fallbacks. While the API keeps answering from a fallback model, the helper sends the full conversation in a new create request on every turn because the API stores none of those turns. The helper goes back to continue requests after a response from the model that you requested. To move the conversation to the fallback model instead, start a new thread from the params with that model and without fallbacks as in Use fallbacks with a thread.
  • Dropped streams. If a stream ends partway through a response, the helper keeps the finished blocks and any text that arrived, and the next turn sends the full conversation in a new create request. The helper doesn’t retry by itself: to re-send the interrupted turn instead, call send() with no messages. If the kept part ends in tool calls, answer them in your next message. If you stop reading a stream after it shows stop_reason: "refusal", the helper treats that turn as a refusal.
  • Other errors. thread_fingerprint_mismatch and thread_unsupported_request errors reach your code. To carry on without thread after a thread_unsupported_request error, create the helper with unsupported_request_behavior set to continue_unthreaded. With that setting, the helper also stops using thread when the first continue request after a replay returns thread_not_found again. The API might be unable to store that conversation. Without that setting, the helper replays on every turn. A tool runner that creates its own thread uses that setting by default.

The SDK’s beta tool runner also uses a thread by default. You can turn off this default when you create the runner.

Streaming. The helper records the response when the stream reaches message_stop, so read the stream to its end. If you stop reading early, end the stream so that the thread is free for the next turn:

  • Python: leave the with block.
  • TypeScript: leave the loop or call abort().
  • Go: call Close.
  • Java and Ruby: call close().
  • C#: dispose of the enumerator. Leaving await foreach does this.
  • PHP: call close().

In C#, the request goes out when you start to read the stream.

In C#, Go, Java, and PHP, after a refusal, thread.LastMessage still returns the previous turn’s response or nothing on a first turn. Read the refusal from the stream’s events.

Changing fields. An update sends nothing and applies to every later turn. Once a thread has a response, the helper refuses a turn that changes system or tools, and the API rejects a change to any other fixed field (see What to send on each request). To change one of these fields, start a new thread from the params, or fork the thread and update the fork before its first turn.

Forking. A fork copies the conversation, the fields, and the request options, and it sends nothing. Its first turn sends the full conversation in a new create request, and the two threads are independent after that. A fork always starts from the whole conversation, not from an earlier response.

Params. The params hold the helper’s fields and the full conversation. Pass them to the method that creates a helper to start a new thread. For example, start one with a different system (see What to send on each request) or with messages cut back to drop later turns. A thread that you start from the params sends every message as you gave it, cache_control breakpoints included, so keep within the limit of 4 (see Prompt caching on a thread). Except in Ruby, the params leave out the request options, so pass those again.

Structured output. Give the output format when you create the helper. A later turn can’t change it. How you get the parsed result depends on the SDK:

  • Python and TypeScript: call thread.parse(...).
  • C#: create the helper with client.Beta.Messages.Thread<T>(...).
  • Go: Send unmarshals into the struct that Params.OutputConfig.Format.Schema points to.
  • Java: create the helper with thread(...) and outputConfig(MyClass.class).
  • PHP: send() sets parsed on the text blocks when outputConfig names a model class.
  • Ruby: pass output_config: {format: MyModel} to thread(...), then read reply.parsed_output.

Errors

The API returns the errors in this table before the model runs. The request uses no tokens, and the thread and its expiry time do not change. error.type is invalid_request_error for the 400 errors and not_found_error for the 404 error.

404thread_not_foundThe API can’t continue the thread.Send the full conversation in a new create request.
400thread_fingerprint_mismatchA fixed field differs from the value stored with the thread. The error message names the fields.Keep the fixed fields the same or start a new thread to change one.
400thread_already_continuedEach response id can be continued once.Continue from the latest response id of the thread. If your client never received that response, replay.

Some requests with thread return a 400 error with no error_code. For example, a continue request returns this error if it has no previous_message_id or if it includes system or tools.

Features that threads don’t support

Threads don’t support these features:

  • Message Batches. A request item that includes thread ends with an invalid_request_error in the batch results.
  • Token counting. A token counting request that includes thread returns a 400 error. Count the full conversation instead, with system and tools.
  • Compaction. Compaction on demand is not available with threads. A request that includes thread returns a 400 error if it sets the compaction parameter or if it sends a compaction block with the compact-2026-09-04 beta header. See Compact a conversation.
  • Context editing except clear_thinking_20251015 with keep: "all".
  • Organizations that have HIPAA readiness enabled.
  • Organizations that have Inference hooks turned on.

The API rejects most requests that threads don’t support with a 400 error and the code thread_unsupported_request. When error.details.unsupported is present, it holds one of these values:

ValueMeaning
context_managementThe request uses context management or compaction that threads don’t support.
cache_controlThe request has more than 4 cache_control breakpoints. See Prompt caching on a thread.
fallbacksThe request sets fallbacks, and your organization can’t use fallbacks with threads.
hipaaYour organization has HIPAA readiness enabled.
inference_hooksYour organization has Inference hooks turned on.

The API can add values to this list. If you get a value that you don’t recognize, send the full conversation without thread. A request that meets several of these conditions gets an error that names only one.

Limitations

  • There is no API to list, read, or delete a thread.
  • Threads are available on the Claude API, Claude Platform on AWS, Claude Models on Google Cloud (Anthropic managed), and Claude in Microsoft Foundry.

Pricing and rate limits

Threads do not change pricing or rate limits.

Data retention

Message threads are not ZDR eligible. Using this feature does not affect your use of other ZDR eligible features. The API holds a thread in memory, encrypted under a server-managed key, never writes it to durable storage, and deletes it no more than 1 hour after its last use.

A thread holds the conversation that the API sends to the model, the system and tools from the create request, and a fingerprint of the fixed fields, which it uses to check later requests. It holds files by reference, so keep every file the conversation uses available while you use the thread.

For ZDR eligibility across all features, see API and data retention.
